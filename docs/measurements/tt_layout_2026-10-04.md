# TT bucket layouts at unchanged memory (#81)

Commit: issue/81 on top of 9648d5a (after #82: `TT_entry` is 32 B, the TT
262144 entries = 8 MB, so a bucket of 8 is 256 B, 4-5 cache lines, not the
8 lines of 184 B entries the issue was written against).
Tool: `tools/bench <depth> -q epd=tools/openings.epd [keep]` (the 130
positions), built per variant in a scratch copy; `lookup_table` (Ascanius-owned)
was not touched in the repo. Machine: i7-1065G7 (L3 8 MB), otherwise idle,
heavy-job lock held.

**Result: no layout is shown faster.** (b) went in anyway at Ascanius' call,
for its lower cache misses with a full table: it searches node for node what
the old layout did (speed_compare main vs (b): +12.3% +- 15.6% nps, no
significant difference, nodes 36503 both).

## Variants

| | layout | ways | memory |
|---|---|---|---|
| L0 | today: `TT_entry table[2^15][8]`, `fill_count[]` apart | 8 | 8 MB + 64 kB |
| L0A | L0, table `alignas(64)` | 8 | same |
| L1 = (a) | `[2^16][4]`, same code | 4 | same |
| L1A | (a), `alignas(64)` | 4 | same |
| L2 = (b) | bucket = 8 keys in one 64 B line + 8 x 24 B entries; fill count in the low byte of key[0] (those bits are the bucket index) | 8 | 8 MB |
| L3 = (c) | 2x buckets of 4 keys (32 B) + 4 x 24 B | 4 | 8 MB |

L2 searches node for node what L0 does, L3 what L1 does (checked at every depth).

Two modes: *reset* clears the TT before each position (as `make bench`);
*keep* never clears it and calls `new_search()` per position (as UCI `go`
does), so buckets run full like in a game.

- With the TT cleared per position, buckets are mostly part-filled and a probe
  only scans `fill_count` entries, so every layout touches about as many lines.
- With a full table the new layouts cut cache misses by 35-55%, but cycles
  move by only ~2-4%: the out-of-order core hides most of the miss latency.
  That ceiling is below what the paired timing can resolve here (+-5%).
- `make speed-compare` (the issue's gate) runs `make bench`, depth 3 with the
  TT cleared per position, where none of this can show.

## If this comes back

The cheaper route to the same few percent is probably a prefetch of the child's
bucket after `make_move()`, not a new layout. A gain this size needs a
lower-noise timer than wall clock on this machine (e.g. `perf stat` cycles in
paired rounds).
